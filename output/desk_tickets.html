3. What would have been simpler as one agent with tools, and why

  • Ticket 102 (rent). The work is a straight line: read the ticket → get_lease_rent_due → get_cash_balance → request_rent_payment. That's about 4 tool calls. The team spent 15 model calls and 33k tokens, mostly passing the same facts from Boss to Facilities to Accounting and back. Facilities' main output was a message to Accounting that repeated what it had just verified.
  • Ticket 103 (discount). The core is one pricing row ($22 cost, $58 list) and one stock row (8 on hand). Three agents each called check_stock_and_pricing on the same SKU in several attempts. One "quote" agent with stock, pricing, cash, and vendor tools would have reached the same $53 answer with a fraction of the calls.
  • Why one agent would still be safe: the important guardrails live in the MCP tools, not in having separate agents. Payments can only be requested, never approved; amounts come from the database; overdrafts and payments to blocked vendors are refused. A single agent hits the same walls.
  • What the team still buys us: separation of duties (only Accounting can file payments, only the Boss can close tickets), focused prompts, and an audit trail that shows who decided what. That's worth having for ticket 101, which touched stock, a vendor bill, cash, and a customer. For single-domain tickets like 102 it's overhead.
